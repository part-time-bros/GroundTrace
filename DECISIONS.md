# Decisions

One line per call made without spec guidance, newest last.

- **Node 22, not 24.** The build container ships Node v22.22.2 and no Node 24 toolchain; 22.x is still Active LTS and provides everything §2 needs (`AsyncLocalStorage`, `node:sqlite`). `engines` is set to `>=22.6.0`.
- **TypeScript 5.9, not 7.0.** TypeScript 7.0.2 is current stable, but `typescript-eslint@8` declares `typescript >=4.8.4 <6.1.0`, so linting would break on TS 7. Pinned to the latest 5.x until the lint toolchain catches up.
- **`docs/BUILD_SPEC.md`.** The spec shipped at the repo root but `CLAUDE.md` references `docs/BUILD_SPEC.md`; moved it there rather than editing every reference.
- **`tsc` for package builds, no bundler.** Only the browser overlay needs bundling (esbuild, one IIFE); everything else ships as plain ESM from `tsc`, which keeps `pnpm build` fast and dependency-light.
- **A fifth package, `packages/overlay`.** §5's overlay is framework-free DOM code that both the demo (imported as a module) and the CLI (served as a prebuilt IIFE for injection into arbitrary apps) need. Keeping it out of `@groundtrace/react` avoids forcing a React dependency on the CLI.
- **No argument-parsing dependency.** Five subcommands and a handful of flags did not justify `commander`; `packages/cli/src/args.ts` is ~60 lines and unit-tested.
- **A third test-claim status, `INCONCLUSIVE`.** §1's spec names VERIFIED and UNVERIFIED. A command that exits 0 but proves no tests (`echo hi`, the §1 acceptance case) is neither: calling it VERIFIED would be exactly the fabricated confidence this tool exists to catch.
- **`TestEvidence` also carries `testsFailed`, `executed`, and `runner`.** §1's own UNVERIFIED example prints "3 failures in the raw output below", which needs a failure count the sketched interface didn't have.
- **pytest is unavailable in the build container**, so its parser is covered by fixture tests only; vitest is verified end-to-end against real passing and real failing suites.
- **`TraceEvent` carries `produces` and `values`.** §4's correlation key ("the `id` from `useTruthValue` matched against `sourceId` from `withTrace`") only works when one server source feeds one DOM value; the demo's single query feeds three. `produces: string[]` makes the join explicit, and `values` lets `VERIFIED` mean "the number on screen equals the number the source returned" rather than "a source nearby succeeded."
- **`EventStore` lives in `@groundtrace/core` from Phase 2, not Phase 4.** It is storage, not classification — Phase 4 still owns every interpretation. `@groundtrace/node` needed somewhere to put finished traces before then.
- **The shared store hangs off a `globalThis` symbol.** Next.js dev re-evaluates route modules on hot reload; a module-level `const` would hand each reloaded copy its own empty store and silently drop every event.
- **Trace ids travel in an `x-groundtrace-id` header, both directions.** Injecting a `__groundtrace` key into the app's own JSON response would mean the tool changes the payload it is supposed to be observing.
- **The call site is captured during render, not inside the effect.** §3's sketch calls `new Error().stack` inside `useEffect`, where the stack shows React's effect-flush frames rather than the calling component. `useTruthValue` captures once per mount at the hook call itself.
- **Change detection uses a structural key, not the raw value.** §3 requires "once per value change, not once per render"; a `[value]` dependency fails that the moment the tracked value is an object, since every render produces a fresh identity.
- **Client events are batched to a microtask.** A page with twenty tracked values makes one collector request instead of twenty, and re-reports within the same tick collapse to the latest value per id.
- **`eslint-plugin-react-hooks` added.** Two deliberate dependency-array deviations needed suppressing, and suppressing a rule that isn't installed is itself a lint error.
- **`classify()` keeps §4's exact signature; `classifyValue`/`buildReport` sit alongside it.** The spec's `classify(clientEvents, serverEvents): ProvenanceNode` describes one value, but the overlay needs the verdict and its reasoning, and the CLI needs every value at once.
- **Every verdict carries a plain-English `reason`.** A classification a developer can't audit is just a different flavour of "Done ✅" — so `VERIFIED` says whether the passthrough was *proven* against a recorded source value or merely assumed because no transform was declared.
- **The tree renderer lives in core.** The terminal report and the browser overlay draw the same `└──` tree from the same code; two renderers would drift apart within a week.
- **Derived server-side values need their own traced step.** Writing the §4 integration test surfaced this: a `growth` figure computed inline in the route arrived in the DOM with no source claiming it, and was correctly classified `UNTRACED`. Wrapping the calculation in `withTraceSync` is the fix, and the §6 demo is built that way.
- **The overlay panel lives in a shadow root.** It gets injected into arbitrary apps, so it must neither inherit the host's CSS nor leak its own — a plain `<div>` would do both.
- **`bippy` is used for exactly one thing: naming the component that rendered a clicked value.** §3 says keep the dependency but don't over-build against it before §5 needs it. `getFiberFromHostInstance` + `getDisplayName`, wrapped in a try/catch that falls back to the SDK's captured call site.
- **Tagged values get `tabindex="0"` and `role="button"`.** §5 asks for keyboard support and the values being tagged are usually `<span>`s, which have no tab stop of their own.
- **Demo seed data is sized away from the fallback constant.** The first seed summed to $182,055 against a hardcoded fallback of $184,293 — close enough that toggling the demo proved nothing visually. Reseeded to $96,159 so the two states are unmistakable at a glance.
- **The demo hosts the collector in its own Next server.** §6 requires `pnpm install && pnpm dev` with no manual setup, so it can't depend on `groundtrace run` being up. Both hosts mount the same `handleCollectorRequest`, and a rewrite maps `/__groundtrace/*` to it so the SDK and overlay need no configuration.
- **`allowedDevOrigins` includes `127.0.0.1`.** Next 16 trusts only `localhost` for dev assets, which 404s the client chunks whenever the demo is opened over an IP — a container, a VM, or a phone on the same network.
- **`agentRules: false` in the demo's Next config.** `next dev` otherwise writes its own `AGENTS.md` and `CLAUDE.md` into `examples/dashboard-demo/`, where they would sit under and compete with the repo's own `CLAUDE.md`.
- **`groundtrace run` is a reverse proxy, not a "paste this script tag" instruction.** §7 promises app + collector + overlay from one command; manual steps in a debugging tool are how you end up debugging the debugger. The proxy forces `accept-encoding: identity` upstream, because rewriting gzip'd HTML as text produces exactly the binary soup you would expect.
- **`verify` reconstructs the client half from `produces`, and marks it unobserved.** A headless run has no DOM to read, so each tracked value gets a stand-in carrying only its id and `valueObserved: false` — never a made-up value. Without that flag the classifier read "no value" as "the value changed" and reported every healthy value as INDIRECT.
- **`verify` says "not scanned" rather than printing a confidence number it can't back.** If the app never came up, the box reports `unknown`. A verification tool that guesses is worse than none, because you would believe it.
- **Tracked ids come from runtime `produces` first, static scan second.** The demo passes ids as JSX expressions (`data-truth-id={id}`), which no regex can resolve; the instrumented server code states its ids outright.
- **`mountOverlay` registers itself on `window.__groundtrace__` and retires any previous instance.** `groundtrace run` injects the overlay into every HTML response, so an app that already mounts its own would otherwise handle every click twice.

## V2

- **§10 drives a real browser instead of reading the DOM itself.** Loading the page through the collector's own proxy makes the app's SDK report the values it actually rendered — first-hand evidence, and it works for apps that host no collector of their own. Manually scraping text out of elements would have re-implemented the SDK, badly.
- **Playwright is resolved at runtime, never depended on.** Forcing a browser download on every user to make one optional feature work is a bad trade; `verify` degrades to the server-side basis and says so.
- **`verify` reports which basis it used.** "3 tracked values" from a real render and "3 tracked values" inferred from server declarations are different claims, and printing them identically would be exactly the quiet overstatement this tool exists to catch.
- **A browser cache with a mismatched Playwright build is discovered, not fatal.** Playwright pins an exact browser build per release; a shared cache provisioned for another version otherwise fails with a bare "Executable doesn't exist".
- **The demo's toggle now defaults from `SIMULATE_API_FAILURE`.** It was hardcoded `useState(true)`, so the env var could never affect anything that loaded the page — including §10's browser scan, which could only ever see the failure state.
- **`waitForApp` bails when the app process exits.** A dev server that refuses to start (Next exits when another instance owns the project directory) will not start ninety seconds later; waiting only delays a diagnosable error.
- **The MCP server is its own package, not a `groundtrace mcp` subcommand.** The CLI would have to depend on `@groundtrace/mcp` while `@groundtrace/mcp` depends on the CLI — a workspace cycle. A separate `groundtrace-mcp` bin avoids it and keeps the MCP SDK and zod out of everyone's CLI install.
- **The read-only MCP tools error when no report exists.** Returning an empty list would be a result an agent could reasonably read as "nothing wrong"; an error that says "run verify_app first — do not assume" cannot be.
- **`init --mcp` never overwrites an existing `groundtrace` entry.** A user who pointed it at a local build or added env of their own means it.
- **The Express adapter reports on `finish` *or* `close`, once.** Both events fire on a normal request, and the store merges same-id traces by concatenating events — so reporting on both duplicated every event in the tree. Found by testing against a real Express server rather than a mock.
- **Adapters are typed structurally; Express, Fastify and `pg` stay out of `dependencies`.** They are dev dependencies so the tests can run against the real frameworks, which is the only way to know the shapes are right.
- **An empty Postgres result is `VERIFIED`, not a fallback.** A query that matches no rows worked; recording it as `FALLBACK_TRIGGERED` would report a healthy query as broken.
- **§14 matches on the DOM, not React's fiber tree.** V2_SPEC sketched a fiber walk, but a rendered text node is a rendered text node: DOM matching works identically for React, Vue, Svelte, and server-rendered HTML, where a fiber walk works for exactly one of them.
- **An automatic match is never presented as proof.** Its reason says "matched automatically, not declared", and an ambiguous match on a *healthy* source is `UNTRACED` rather than a guess. An ambiguous match on a *failed* source still reports `FALLBACK` — a possible fallback is the case worth being loud about.
- **The auto-tagger reports once per change, like the React SDK.** Otherwise a 1s polling interval re-sends every value on the page every second.
